# SDD Flow для VS Code

Панель для разработчиков, которые работают по AI-Native процессу (OpenSpec SDD): показывает, на каком шаге задача, что её блокирует и что делать дальше, а вместо запоминания команд даёт кнопки — расширение само создаёт ветку, запускает `/cex-sdd:apply`, проверки, подключает и обновляет спеки.

Работает в VS Code и Cursor, в любом кодовом репозитории процесса, к которому подключены спеки OpenSpec. Для WebStorm не предназначено. Аналитики работают командами `/opsx:*` в репозитории спек, расширение им не нужно.

## Установка

Нужен VS Code 1.85+ и команда `code` в PATH (VS Code → `Shell Command: Install 'code' command in PATH`).
`code --install-extension` не понимает ссылок, поэтому файл сначала скачивается, затем устанавливается.

**macOS / Linux**

```bash
curl -fL -o /tmp/cex-sdd-vscode.vsix https://github.com/webdozerz/cex-sdd-vscode/releases/latest/download/cex-sdd-vscode.vsix \
  && code --install-extension /tmp/cex-sdd-vscode.vsix --force
```

**Windows (PowerShell)**

```powershell
Invoke-WebRequest https://github.com/webdozerz/cex-sdd-vscode/releases/latest/download/cex-sdd-vscode.vsix -OutFile $env:TEMP\cex-sdd-vscode.vsix
code --install-extension $env:TEMP\cex-sdd-vscode.vsix --force
```

**Cursor** — то же самое, но вместо `code` команда `cursor` (Cursor → `Shell Command: Install 'cursor' command`).

Те же команды обновляют расширение до последней версии. После установки перезагрузите окно (`Developer: Reload Window`).

Без терминала: скачайте `cex-sdd-vscode.vsix` со страницы [Releases](https://github.com/webdozerz/cex-sdd-vscode/releases), затем в VS Code **Extensions** → меню `…` → **Install from VSIX…**.

## Что нужно для работы

| Что | Зачем | Как поставить |
|---|---|---|
| Claude Code (расширение VS Code или CLI `claude`) | кнопки запускают `/cex-sdd:apply` и `/cex-sdd:spec-gap` | [claude.com/claude-code](https://claude.com/claude-code) |
| Плагин `cex-sdd` из маркетплейса плагинов компании | команды `/cex-sdd:*` | кнопка **Установить плагин cex-sdd** в панели, или вручную: `claude plugin marketplace add <адрес маркетплейса>` и `claude plugin install cex-sdd@<маркетплейс>` |
| Сабмодуль спек OpenSpec в репозитории | откуда берутся change, `tasks.md`, tier | кнопка **Подключить спеки** (`pnpm specs`, `make specs` или `git submodule update --init`) |
| `gh` (GitHub CLI), авторизованный | прогресс плана по PR (`Шаги plan.md: …`) | `brew install gh` и `gh auth login`; без него прогресс считается по галочкам в `plan.md` |
| `git` 2.15+ | ветки, сабмодуль, метки `sdd-temp` | обычно уже есть |

Доступ на чтение к репозиторию спек и маркетплейсу плагинов нужен самому разработчику — расширение пользуется вашими `git` и `gh`.

## Первый запуск

1. Откройте кодовый репозиторий процесса и панель **SDD Flow** в Activity Bar.
2. Если панель просит — нажмите **Установить плагин cex-sdd** и **Подключить спеки**, затем перезагрузите окно.
3. На `develop` нажмите **Начать задачу**: выберите change, подтвердите ключ своей подзадачи и slug. Расширение создаст ветку `feat/SE-130-<slug>` (для tier 1–2 сначала `…-design`) от `origin/develop` и откроет Claude Code с `/cex-sdd:apply`.
4. Дальше панель показывает текущий шаг, стопперы и следующий шаг; главная кнопка меняется по ситуации.

Если задачи нет в списке — её change ещё не в спеках, закреплённых в `develop`: нужен отдельный PR `chore(SE-…): bump openspec` (см. «Если что-то не работает»).

## Что умеет

### Панель «SDD Flow»

- **Главная кнопка** на текущую ситуацию и вторичные действия.
- **Лента шагов** (8 из 11 процесса, только касающиеся разработчика): спека → дизайн и план → реализация → PR → dev → rc → приёмка → архив.
- **Что блокирует**: стопперы с подсказкой и кнопкой «Открыть».
- **Сейчас в этой ветке**: шаг плана, который делается в текущей ветке.
- **План**: прогресс по шагам из `docs/changes/<change>/plan.md` по всем веткам и PR задачи.
- **Дальше**: одно следующее действие.

В status bar: `SE-130 🛑1 ⚠2`, клик открывает панель.

### Кнопки и что за ними

| Кнопка | Что делает | Кто выполняет |
|---|---|---|
| **Начать задачу** | мастер: выбрать change → ключ вашей задачи → slug → ветка `feat/SE-130-slug` (для tier 1–2 сначала `…-design`) от `origin/develop` → запуск `/cex-sdd:apply` | расширение + Claude Code |
| **Спроектировать и спланировать / Продолжить по плану** | `/cex-sdd:apply <change>`: агент сам смотрит на состояние (design.md, plan.md, мерж дизайна) и ждёт вашего согласия | Claude Code |
| **Расхождение со спекой** | предупреждение про уязвимости → ввод описания → `/cex-sdd:spec-gap`. Описание нигде не сохраняется | Claude Code |
| **Быстрая / полная проверка** | `pnpm verify:fast` / `pnpm verify` (или `make verify`) в терминале | расширение |
| **Подключить спеки** | `pnpm specs` (или `git submodule update --init <путь>`) | расширение |
| **Обновить спеки** | `git submodule update --remote <путь>` после подтверждения; коммит `chore(SE-…): bump openspec` делается отдельно | расширение |
| **Выбрать change** | ручная привязка ветки к change, запоминается | расширение |
| **Установить / включить / обновить плагин cex-sdd** | команды `claude plugin …` в терминале после подтверждения | расширение |

Состояние плагина читается из файлов Claude Code (`~/.claude/plugins/installed_plugins.json`, `known_marketplaces.json`, `enabledPlugins` в пользовательских и проектных настройках), запуск CLI не нужен. Команды `/cex-sdd:*` не запускаются, пока плагина нет: расширение предлагает его поставить.

Запрос в Claude Code передаётся командой `claude-vscode.primaryEditor.open`; если её нет — через `claude` в терминале. Запрос дополнительно копируется в буфер обмена.

### Как определяется change

Ключ `SE-NNN` берётся из ветки (`feat/SE-130-limits-form`). Ключ может быть подзадачей, а change назван по родителю (`se-123-…`), поэтому поиск идёт по цепочке:

1. change, выбранный вручную или в мастере для этой ветки;
2. ключ подзадачи в заголовке группы `tasks.md`: `## 2. client-fe (SE-130)`;
3. имя change начинается с ключа ветки (`se-123-…` для `SE-123`), включая архив;
4. ветка меняет `docs/changes/<change>/` (после первого `/cex-sdd:apply`).

Если ничего не подошло, расширение предлагает выбрать change. Связь «подзадача → родитель» в Jira пока не используется.

Какому репозиторию из `affected_areas` соответствует проект — по адресу `origin` или имени папки; можно задать настройкой `sddFlow.repoId`.

| Что читается | Откуда |
|---|---|
| Спека change | `openspec/changes/<change>/` (сабмодуль, только чтение), архив — `…/archive/<дата>-<change>/` |
| Tier, области, ключи | `meta.yaml`, `.openspec.yaml`, `tasks.md` |
| Дизайн, план, расхождения | `docs/changes/<change>/`: `design.md`, `plan.md`, `spec-gaps.md` |
| Дизайн смержен | `git log origin/develop -- docs/changes/<change>/design.md` |
| Приёмка | `acceptance.md` (`Результат: принято`) |

### Прогресс плана по нескольким PR

**Основной способ — id шагов и PR.** У шага в `plan.md` постоянный id: `- [ ] <!-- step: base --> …`. PR не правит `plan.md`, а пишет в описании строку `Шаги plan.md: base, modals`. Расширение читает PR задачи через `gh` (`gh pr list --search "<KEY> in:title"`): смерженный PR → шаг «в develop», открытый → «в PR» (номер и ветка), открытый из текущей ветки → «в этой ветке». Закрытый без мержа не засчитывается.

**Запасной способ — галочки**, если у шага нет id, ни один PR на него не ссылается или `gh` недоступен:

Каждый шаг `plan.md` — отдельный PR в своей ветке, и галочка ставится в `plan.md` этой ветки. Поэтому расширение сводит прогресс из трёх мест:

- **в develop** — шаг отмечен в `plan.md` на `origin/develop` (PR смержен); шаг дизайна засчитывается, когда `design.md` в `develop`, даже без галочки;
- **в PR** — шаг отмечен в другой удалённой ветке с ключом задачи (`origin/*SE-130*`), PR ещё не смержен;
- **в этой ветке** — отмечен в текущем рабочем дереве.

Шаги сравниваются по тексту без разметки, а если шаг переформулировали в своей ветке — по разделу плана и номеру шага в нём. «Дальше» показывает первый шаг, которого нет ни в одном из трёх мест.

### Временные исключения

Сознательное «пока так» (например, право отложено до бэкенда) описывается в двух местах:

- метка в коде одной строкой, для любого языка: `// sdd-temp(SE-130): право не проверяется до SE-131`;
- строка таблицы в разделе `## Временные исключения` в `design.md` (что, где, почему, когда снять).

Расширение ищет метки с ключом задачи (`git grep`, без `*.md`, `vendor/`, `third_party/`, `node_modules/`) и показывает их списком с переходом к строке. Пока идёт работа — это информация; когда вне раздела «Интеграция» шагов не осталось — ошибка «Не сняты временные исключения». Если число меток и строк таблицы расходится или таблицы нет — предупреждение.

### Стопперы

| Стоппер | Уровень |
|---|---|
| Не установлен или отключён плагин `cex-sdd` (без него нет `/cex-sdd:*`) | ошибка; кнопки запуска команд перестают быть главными |
| Плагин `cex-sdd` старше 0.6.0 (берёт ключ родителя вместо подзадачи) | предупреждение |
| Сабмодуль OpenSpec не подключён | ошибка |
| Change не найден (в `feat/` ветке) | ошибка; в `fix/` ветке — инфо про метку `no-spec` |
| Приёмка QA: не принято | ошибка |
| Нет `design.md` и `plan.md` | предупреждение |
| tier 1–2: дизайн написан, но не смержен в develop (код ждёт мержа design PR) | предупреждение |
| Открытое расхождение со спекой (`spec-gaps.md`, поле «Решение» не заполнено) | предупреждение |
| Нет `tasks.md` или группы задач репозитория | предупреждение |
| Репозитория нет в `affected_areas` | инфо |

Шаги PR, dev и rc показываются как «неизвестно», пока не подключён GitHub.

## Если что-то не работает

- **Задачи нет в списке мастера / «Не найден change».** Change смержен в OpenSpec, но в `develop` закреплена старая версия спек. Нужен отдельный PR: ветка `chore/SE-<ключ>-bump-openspec` от `develop`, `git submodule update --init --remote <путь сабмодуля>`, коммит `chore(SE-<ключ>): bump openspec`. После мержа — `git pull` и `git submodule update --init`. Если в `main` OpenSpec активных changes нет совсем, расширение так и скажет: обновлять нечего, change появится после Gate 1.
- **«Не установлен плагин cex-sdd»**, хотя ставили. Перезагрузите окно; проверьте `claude plugin list` — плагин должен быть `enabled`. Обновление: `claude plugin marketplace update <маркетплейс>` и `claude plugin update cex-sdd@<маркетплейс>`.
- **«Не удалось создать ветку: index.lock».** Другой git-процесс держал индекс; мастер повторяет попытку сам. Если ошибка осталась — закройте другие git-операции и повторите. Если git-процессов нет, а `.git/index.lock` остался, его можно удалить.
- **Прогресс плана «сбросился» в новой ветке.** Галочки ставятся в `plan.md` той ветки, где делается шаг; расширение сводит их из `develop` и ваших веток с ключом задачи, но только из запушенных. Надёжнее — id шагов и строка `Шаги plan.md: …` в описании PR (нужен `gh`).
- **Запрос не отправился в Claude Code.** Он подставляется в поле ввода и копируется в буфер обмена — вставьте и отправьте.

## Разработка

```bash
npm install
npm run watch        # пересборка при изменениях; F5 запускает Extension Development Host
npm test             # тесты ядра: разбор спек и плана, поиск change, лента, стопперы, прогресс, плагин
npm run type-check
npm run package      # проверка типов + тесты + сборка cex-sdd-vscode-<версия>.vsix
```

Ядро (`src/core`, `src/ui/render.ts`) не зависит от `vscode` и покрыто тестами; `src/extension.ts`, `src/actions.ts`, `src/git.ts`, `src/gitprobe.ts`, `src/ui/FlowViewProvider.ts` — тонкий слой над API VS Code, git и gh.

**Выпуск версии:** поднять `version` в `package.json` и записать изменения в `CHANGELOG.md`, затем

```bash
npm run package
cp cex-sdd-vscode-<версия>.vsix /tmp/cex-sdd-vscode.vsix
gh release create v<версия> /tmp/cex-sdd-vscode.vsix --title v<версия> --notes-file <заметки>
```

Имя файла в релизе всегда `cex-sdd-vscode.vsix` — на него ссылается команда установки (`releases/latest/download/…`).
