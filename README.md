# SDD Flow для VS Code

Панель для разработчиков, которые работают по AI-Native процессу (OpenSpec SDD): показывает, на каком шаге задача, что её блокирует и что делать дальше, а вместо запоминания команд даёт кнопки — расширение само создаёт ветку, запускает `/cex-sdd:apply`, проверки, подключает и обновляет спеки.

Работает в VS Code и Cursor, в любом кодовом репозитории процесса, к которому подключены спеки OpenSpec. Для WebStorm не предназначено. Аналитики работают командами `/opsx:*` в репозитории спек, расширение им не нужно.

## Установка

Репозиторий приватный, поэтому релиз скачивается через `gh` (GitHub CLI) с вашим доступом к репозиторию.

Нужны:
- VS Code 1.85+ и команда `code` в PATH (VS Code → `Shell Command: Install 'code' command in PATH`);
- `gh`, авторизованный в GitHub: `brew install gh` и `gh auth login`;
- доступ на чтение к `webdozerz/cex-sdd-vscode` — попросите у владельца репозитория.

`code --install-extension` не понимает ссылок, поэтому файл сначала скачивается, затем устанавливается.

**macOS / Linux**

```bash
gh release download --repo webdozerz/cex-sdd-vscode --pattern cex-sdd-vscode.vsix --dir /tmp --clobber \
  && code --install-extension /tmp/cex-sdd-vscode.vsix --force
```

**Windows (PowerShell)**

```powershell
gh release download --repo webdozerz/cex-sdd-vscode --pattern cex-sdd-vscode.vsix --dir $env:TEMP --clobber
code --install-extension $env:TEMP\cex-sdd-vscode.vsix --force
```

**Cursor** — то же самое, но вместо `code` команда `cursor` (Cursor → `Shell Command: Install 'cursor' command`).

Те же команды обновляют расширение до последней версии: `gh release download` без тега берёт последний релиз. После установки перезагрузите окно (`Developer: Reload Window`).

Без терминала: войдите в GitHub в браузере, скачайте `cex-sdd-vscode.vsix` со страницы [Releases](https://github.com/webdozerz/cex-sdd-vscode/releases), затем в VS Code **Extensions** → меню `…` → **Install from VSIX…**.

**Если `gh release download` пишет `release not found` или `HTTP 404`** — у вашего аккаунта нет доступа к репозиторию или `gh` авторизован под другим аккаунтом: проверьте `gh auth status`.

## Что нужно для работы

| Что | Зачем | Как поставить |
|---|---|---|
| Claude Code (расширение VS Code или CLI `claude`) | кнопки запускают `/cex-sdd:apply`, `/cex-sdd:spec-gap` и `/cex-sdd:spec-update` | [claude.com/claude-code](https://claude.com/claude-code) |
| Плагин `cex-sdd` из маркетплейса плагинов компании | команды `/cex-sdd:*` | кнопка **Установить плагин cex-sdd** в панели, или вручную: `claude plugin marketplace add <адрес маркетплейса>` и `claude plugin install cex-sdd@<маркетплейс>` |
| Сабмодуль спек OpenSpec в репозитории | откуда берутся change, `tasks.md`, tier | кнопка **Подключить спеки** (`pnpm specs`, `make specs` или `git submodule update --init`) |
| `gh` (GitHub CLI), авторизованный | прогресс плана по PR (`Шаги plan.md: …`) | `brew install gh` и `gh auth login`; без него прогресс считается по галочкам в `plan.md` |
| `git` 2.15+ | ветки, сабмодуль, метки `sdd-temp` | обычно уже есть |

Доступ на чтение к репозиторию спек и маркетплейсу плагинов нужен самому разработчику — расширение пользуется вашими `git` и `gh`.

## Первый запуск

1. Откройте кодовый репозиторий процесса и панель **SDD Flow** в Activity Bar.
2. Если панель просит — нажмите **Установить плагин cex-sdd** и **Подключить спеки**, затем перезагрузите окно.
3. На `develop` нажмите **Начать задачу**: выберите change, подтвердите ключ своей подзадачи и slug. Расширение создаст ветку `feat/TN-130-<slug>` (для tier 1–2 сначала `…-design`) от `origin/develop` и откроет Claude Code с `/cex-sdd:apply`.
4. Дальше панель показывает текущий шаг, стопперы и следующий шаг; главная кнопка меняется по ситуации.

Если задачи нет в списке — её change ещё не в спеках, закреплённых в `develop`: нужен отдельный PR `chore(TN-…): bump openspec` (см. «Если что-то не работает»).

## Что умеет

### Панель «SDD Flow»

- **Главная кнопка** на текущую ситуацию и вторичные действия.
- **Лента шагов** (8 из 11 процесса, только касающиеся разработчика): спека → дизайн и план → реализация → PR → dev → rc → приёмка → архив.
- **Что блокирует**: стопперы. В каждом — почему это мешает, строка «Что сделать» с конкретным действием и, где можно, кнопка этого действия прямо в карточке и ссылка на нужный файл.
- **Сейчас в этой ветке**: шаг плана, который делается в текущей ветке.
- **План**: прогресс по шагам из `docs/changes/<change>/plan.md` по всем веткам и PR задачи.
- **AI-ревью**: состояние «прохода 0» у PR текущей ветки — со ссылкой на комментарий или лог прогона.
- **Дальше**: одно следующее действие.

В status bar: `TN-130 🛑1 ⚠2`, клик открывает панель.

### Кнопки и что за ними

| Кнопка | Что делает | Кто выполняет |
|---|---|---|
| **Начать задачу** | мастер: выбрать change → ключ вашей задачи → slug → ветка `feat/TN-130-slug` (для tier 1–2 сначала `…-design`) от `origin/develop` → запуск `/cex-sdd:apply` | расширение + Claude Code |
| **Спроектировать и спланировать / Продолжить по плану** | `/cex-sdd:apply <change>`: агент сам смотрит на состояние (design.md, plan.md, мерж дизайна) и ждёт вашего согласия | Claude Code |
| **Расхождение со спекой** | предупреждение про уязвимости → ввод описания → `/cex-sdd:spec-gap`. Описание нигде не сохраняется | Claude Code |
| **Обновить change в OpenSpec** | появляется, когда в `spec-gaps.md` есть решение «обновить change» без ссылки на правку или когда задачи своей группы пора отметить в `tasks.md`. Предупреждение про уязвимости → `/cex-sdd:spec-update <change>` с тем, что нашла панель. Скилл готовит правку в отдельном клоне OpenSpec и ждёт вашего согласия. Нужно право записи в OpenSpec — оно у лидов | Claude Code |
| **Запустить / перезапустить AI-ревью** | есть, когда в репозитории есть `.github/workflows/ai-review.yml`, а у ветки — открытый PR не в черновике. После подтверждения метка `ai-review` ставится на PR заново, и workflow проверяет дифф | расширение (`gh`) |
| **Быстрая / полная проверка** | `pnpm verify:fast` / `pnpm verify` (или `make verify`) в терминале | расширение |
| **Подключить спеки** | `pnpm specs` (или `git submodule update --init <путь>`) | расширение |
| **Обновить спеки** | есть всегда, а также иконка ☁ в заголовке панели. После подтверждения — `git submodule update --init --remote <путь>`: сабмодуль спек до свежего main OpenSpec. Новый commit сабмодуля, если его оставлять в ветке, уходит отдельным PR `chore(TN-…): bump openspec` | расширение |
| **Выбрать change** | ручная привязка ветки к change, запоминается | расширение |
| **Установить / включить / обновить плагин cex-sdd** | команды `claude plugin …` в терминале после подтверждения | расширение |

Состояние плагина читается из файлов Claude Code (`~/.claude/plugins/installed_plugins.json`, `known_marketplaces.json`, `enabledPlugins` в пользовательских и проектных настройках), запуск CLI не нужен. Команды `/cex-sdd:*` не запускаются, пока плагина нет: расширение предлагает его поставить.

Запрос в Claude Code передаётся командой `claude-vscode.primaryEditor.open`; если её нет — через `claude` в терминале. Запрос дополнительно копируется в буфер обмена.

### Как определяется change

Ключ задачи трекера берётся из ветки (`feat/TN-130-limits-form`). В примерах `TN` (TaskName) — условный ключ проекта: подходит ключ любого проекта трекера, заглавными буквами, в начале имени ветки или сразу после `feat/`, `fix/` и т. п. Ключ может быть подзадачей, а change назван по родителю (`tn-123-…`), поэтому поиск идёт по цепочке:

1. change, выбранный вручную или в мастере для этой ветки;
2. ключ подзадачи в заголовке группы `tasks.md`: `## 2. client-fe (TN-130)`;
3. имя change начинается с ключа ветки (`tn-123-…` для `TN-123`), включая архив;
4. ветка меняет `docs/changes/<change>/` (после первого `/cex-sdd:apply`).

Если ничего не подошло, расширение предлагает выбрать change. Связь «подзадача → родитель» в Jira пока не используется.

Какому репозиторию из `affected_areas` соответствует проект — по адресу `origin` или имени папки; можно задать настройкой `sddFlow.repoId`.

| Что читается | Откуда |
|---|---|
| Спека change | `openspec/changes/<change>/` (сабмодуль, только чтение), архив — `…/archive/<дата>-<change>/` |
| Tier, области, ключи | `meta.yaml`, `.openspec.yaml`, `tasks.md` |
| Дизайн, план, расхождения | `docs/changes/<change>/` или, если план ведётся в спеке, `openspec/changes/<change>/plans/<репозиторий>/`: `design.md`, `plan.md`, `spec-gaps.md` |
| Дизайн смержен | план в кодовом репо — `git log origin/develop -- docs/changes/<change>/design.md`; план в спеке — он виден в сабмодуле, значит уже в `main` спек |
| Приёмка | `acceptance.md` (`Результат: принято`) |

### Правка change в OpenSpec

Когда реализация расходится со спекой, `/cex-sdd:spec-gap` записывает расхождение в `spec-gaps.md`, а тимлид заполняет поле «Решение»: обновить change, баг кода или вне рамок. Решения «обновить change» лид вносит в OpenSpec скиллом `/cex-sdd:spec-update` (плагин `cex-sdd` 0.7.0+). Скилл:

- работает в отдельном клоне OpenSpec во временном каталоге — сабмодуль спек только читается;
- делает одну правку на change: если PR по change уже открыт, коммит идёт в него;
- прогоняет `npm run check` и `npm run lint:contracts`, PR идёт через Gate 1;
- дописывает к «Решению» записи ссылку `→ OpenSpec #N`.

Расширение читает записи `spec-gaps.md`:

- «Решение» пустое, в `<…>` или `_(тимлид)_` — расхождение открыто, ждёт тимлида;
- «обновить change» без ссылки `OpenSpec #N` (или адреса PR в OpenSpec) — предупреждение и кнопка **Обновить change в OpenSpec**. Код с отступлением не мержится, пока правка не открыта; в PR кода — строка «Правка спеки: OpenSpec#NNN» (её проверяет CI `conventions`);
- ссылка есть — правка открыта, стоппера нет. Поле «PR спеки» записей, сделанных расширением до 0.7.0, тоже читается.

**Отметка задач.** После мержа PR кода лид тем же скиллом отмечает задачи своей группы в `tasks.md` OpenSpec — без этого change не архивируется. Если все шаги раздела плана `## tasks.md N.M` смержены, а задача в `tasks.md` сабмодуля не отмечена, панель напоминает об этом и показывает ту же кнопку. Если задачи уже отмечены в OpenSpec, но спеки в `develop` старые, — обновите спеки.

После мержа правки — **Обновить спеки** и отдельный коммит `chore(TN-…): bump openspec`.

### AI-ревью

В кодовых репо есть workflow «AI review» (`.github/workflows/ai-review.yml`): при открытии PR или по метке `ai-review` Claude проверяет дифф и оставляет до 5 замечаний одним комментарием. Расширение читает через `gh` PR текущей ветки и показывает:

| Состояние | Когда |
|---|---|
| черновик | PR в черновике: ревью запустится после Ready for review |
| идёт AI-ревью | прогон в очереди или выполняется; ссылка на лог |
| замечания готовы | есть комментарий Claude; ссылка на него |
| прогон без комментария | прогон прошёл, а комментария нет — обычно в репозитории не задан секрет Claude |
| AI-ревью упало | прогон завершился ошибкой; ссылка на лог |
| не запускалось | PR открыт до появления workflow или последний прогон пропущен |

Кнопка **Запустить / Перезапустить AI-ревью** снимает и снова ставит метку `ai-review`: workflow срабатывает только на установку метки. Каждый прогон тратит токены Claude. Статус обновляется раз в минуту, сразу — по кнопке «Обновить».

### План в репозитории спек

По умолчанию `design.md`, `plan.md` и `spec-gaps.md` лежат в кодовом репо, в `docs/changes/<change>/`. Если в проекте план ведётся в спеке, расширение читает их из `openspec/changes/<change>/plans/<репозиторий>/`. Вариант выбирается так:

1. настройка `sddFlow.plansLocation` (`code` или `spec`);
2. иначе — `plans: code` или `plans: spec` в `.cex-sdd.yaml` в корне репозитория (тот же файл читает плагин `cex-sdd`);
3. иначе — есть ли у change каталог `plans/<репозиторий>/` в спеке;
4. иначе — кодовый репо.

В шапке панели тогда тег «план в спеке». План в сабмодуле — это уже смерженный в `main` спек вариант, поэтому дизайн считается смерженным. Прогресс сводится с `plan.md` из `origin/main` сабмодуля и с PR кодового репо (`Шаги plan.md: …`). Правки плана, галочки шагов и записи расхождений в этом варианте идут PR в репозиторий спек.

### Прогресс плана по нескольким PR

**Основной способ — id шагов и PR.** У шага в `plan.md` постоянный id: `- [ ] <!-- step: base --> …`. PR не правит `plan.md`, а пишет в описании строку `Шаги plan.md: base, modals`. Расширение читает PR задачи через `gh` (`gh pr list --search "<KEY> in:title"`): смерженный PR → шаг «в develop», открытый → «в PR» (номер и ветка), открытый из текущей ветки → «в этой ветке». Закрытый без мержа не засчитывается.

**Запасной способ — галочки**, если у шага нет id, ни один PR на него не ссылается или `gh` недоступен:

Каждый шаг `plan.md` — отдельный PR в своей ветке, и галочка ставится в `plan.md` этой ветки. Поэтому расширение сводит прогресс из трёх мест:

- **в develop** — шаг отмечен в `plan.md` на `origin/develop` (PR смержен); шаг дизайна засчитывается, когда `design.md` в `develop`, даже без галочки;
- **в PR** — шаг отмечен в другой удалённой ветке с ключом задачи (`origin/*TN-130*`), PR ещё не смержен;
- **в этой ветке** — отмечен в текущем рабочем дереве.

Шаги сравниваются по тексту без разметки, а если шаг переформулировали в своей ветке — по разделу плана и номеру шага в нём. «Дальше» показывает первый шаг, которого нет ни в одном из трёх мест.

### Временные исключения

Сознательное «пока так» (например, право отложено до бэкенда) описывается в двух местах:

- метка в коде одной строкой, для любого языка: `// sdd-temp(TN-130): право не проверяется до TN-131`;
- строка таблицы в разделе `## Временные исключения` в `design.md` (что, где, почему, когда снять).

Расширение ищет метки с ключом задачи (`git grep`, без `*.md`, `vendor/`, `third_party/`, `node_modules/`) и показывает их списком с переходом к строке. Пока идёт работа — это информация; когда вне раздела «Интеграция» шагов не осталось — ошибка «Не сняты временные исключения». Если число меток и строк таблицы расходится или таблицы нет — предупреждение.

### Стопперы

| Стоппер | Уровень |
|---|---|
| Не установлен или отключён плагин `cex-sdd` (без него нет `/cex-sdd:*`) | ошибка; кнопки запуска команд перестают быть главными |
| Плагин `cex-sdd` старше 0.7.0 (нет `/cex-sdd:spec-update`; до 0.6.0 — ещё и ключ родителя вместо подзадачи) | предупреждение |
| Сабмодуль OpenSpec не подключён | ошибка |
| Спеки в рабочей копии отстают от закреплённых в ветке (не сделали `git submodule update` после `git pull`) | предупреждение, кнопка «Синхронизировать спеки» |
| Файлы change в main OpenSpec новее закреплённых в ветке (решения, задачи, план) | предупреждение, кнопка «Обновить спеки до main OpenSpec» |
| Спеки обновлены локально, bump не закоммичен | инфо |
| Change не найден (в `feat/` ветке) | ошибка; в `fix/` ветке — инфо про метку `no-spec` |
| Приёмка QA: не принято | ошибка |
| Нет `design.md` и `plan.md` | предупреждение |
| tier 1–2: дизайн написан, но не смержен в develop (код ждёт мержа design PR) | предупреждение |
| Открытое расхождение со спекой (`spec-gaps.md`, поле «Решение» не заполнено или `_(тимлид)_`) | предупреждение |
| Решено «обновить change», а ссылки `→ OpenSpec #N` нет | предупреждение |
| Шаги плана задачи смержены, а в `tasks.md` OpenSpec задача не отмечена | инфо |
| Нет `tasks.md` или группы задач репозитория | предупреждение |
| Репозитория нет в `affected_areas` | инфо |

Шаги PR, dev и rc показываются как «неизвестно»: статус PR в ленту пока не подключён.

## Настройки

| Настройка | По умолчанию | Что делает |
|---|---|---|
| `sddFlow.repoId` | `auto` | Какому репозиторию из `affected_areas` соответствует проект. `auto` — по адресу `origin` или имени папки |
| `sddFlow.plansLocation` | `auto` | Где лежат `design.md`, `plan.md` и `spec-gaps.md`: `code` — `docs/changes/<change>/`, `spec` — `openspec/changes/<change>/plans/<репозиторий>/`, `auto` — `.cex-sdd.yaml`, затем наличие каталога в спеке |

Команды (палитра, категория **SDD Flow**): «Начать задачу», «Продолжить change», «Расхождение со спекой», «Обновить change в OpenSpec», «Установить или обновить плагин cex-sdd», «Полная проверка», «Быстрая проверка», «Выбрать change вручную», «Сбросить выбор, определять по ветке», «Обновить», «Показать панель».

## Если что-то не работает

- **Задачи нет в списке мастера / «Не найден change».** Change смержен в OpenSpec, но в `develop` закреплена старая версия спек. Нужен отдельный PR: ветка `chore/TN-<ключ>-bump-openspec` от `develop`, `git submodule update --init --remote <путь сабмодуля>`, коммит `chore(TN-<ключ>): bump openspec`. После мержа — `git pull` и `git submodule update --init`. Если в `main` OpenSpec активных changes нет совсем, расширение так и скажет: обновлять нечего, change появится после Gate 1.
- **«Не установлен плагин cex-sdd»**, хотя ставили. Перезагрузите окно; проверьте `claude plugin list` — плагин должен быть `enabled`. Обновление: `claude plugin marketplace update <маркетплейс>` и `claude plugin update cex-sdd@<маркетплейс>`.
- **«Не удалось создать ветку: index.lock».** Другой git-процесс держал индекс; мастер повторяет попытку сам. Если ошибка осталась — закройте другие git-операции и повторите. Если git-процессов нет, а `.git/index.lock` остался, его можно удалить.
- **Прогресс плана «сбросился» в новой ветке.** Галочки ставятся в `plan.md` той ветки, где делается шаг; расширение сводит их из `develop` и ваших веток с ключом задачи, но только из запушенных. Надёжнее — id шагов и строка `Шаги plan.md: …` в описании PR (нужен `gh`).
- **Запрос не отправился в Claude Code.** Он подставляется в поле ввода и копируется в буфер обмена — вставьте и отправьте.

## Разработка

```bash
npm install
npm run watch        # пересборка при изменениях; F5 запускает Extension Development Host
npm test             # тесты ядра: разбор спек и плана, поиск change, лента, стопперы, прогресс, плагин
npm run type-check
npm run package      # проверка типов + тесты + сборка cex-sdd-vscode-<версия>.vsix
```

Ядро (`src/core`, `src/ui/render.ts`) не зависит от `vscode` и покрыто тестами; `src/extension.ts`, `src/actions.ts`, `src/git.ts`, `src/gitprobe.ts`, `src/ui/FlowViewProvider.ts` — тонкий слой над API VS Code, git и gh.

**Выпуск версии:** поднять `version` в `package.json` и записать изменения в `CHANGELOG.md`, затем

```bash
npm run package
cp cex-sdd-vscode-<версия>.vsix /tmp/cex-sdd-vscode.vsix
gh release create v<версия> /tmp/cex-sdd-vscode.vsix --title v<версия> --notes-file <заметки>
```

Имя файла в релизе всегда `cex-sdd-vscode.vsix` — на него ссылается команда установки (`gh release download --pattern cex-sdd-vscode.vsix`).
